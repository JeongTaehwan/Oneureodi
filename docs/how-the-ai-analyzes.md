# AI가 데이트 코스를 찾아내는 방법

이 프로젝트에서 실제로 돌아가는 파이프라인을 기준으로, 다른 프로젝트에도 옮겨 쓸 수 있는 방법을 정리한다.
코드 위치는 `apps/server/src` 기준.

## 0. 한 줄 요약

**AI에게 "추천해줘"라고 시키지 않는다.** 데이터 수집은 API, 판단은 코드, AI는 "비정형 글을 구조화하는 일"과 "후보 안에서 조합을 고르는 일" 두 가지만 맡는다.

```
입력 ─▶ 좌표 변환 ─▶ [지도 검색 ‖ 웹 조사] ─▶ 이름 매칭 ─▶ 코드 필터 ─▶ AI 조합 ─▶ 코드 검증 ─▶ 경로·시간표 ─▶ 결과
        (카카오)      (카카오)  (Tavily+Gemini)                (주차·시간)   (Gemini)   (예산·id·시간)  (카카오)
```

한 번의 추천에 AI 호출은 4번(추출 3 + 조합 1), 나머지는 전부 결정적인 코드다.

## 1. 역할을 나누는 원칙

| 일 | 누가 | 이유 |
| --- | --- | --- |
| 장소 좌표·카테고리·주소 | 카카오 로컬 API | AI는 지어낸다. 존재하는 장소만 후보로 |
| "어떤 글에 어떤 가게가 나오나" | 검색 API + AI 추출 | 비정형 → 구조화는 AI가 잘하는 일 |
| 주차·시간·예산 필터 | 코드 | 규칙이 명확한 건 AI에 맡기면 매번 다르게 판단한다 |
| 후보 60개 중 코스 5개 조합 | AI | 성향·분위기·순서 같은 "취향" 판단 |
| AI 출력 검증 | 코드 | 없는 id, 예산 초과, 시간 안 맞는 코스를 걸러낸다 |
| 이동 경로·소요 시간 | 카카오 경로 API | AI는 "버스 10분"을 지어낸다 |

핵심은 **AI 출력을 그대로 믿지 않는 것**. `recommend.service.ts`의 `materialize`와 `applySchedule`이 AI가 낸 코스를 다시 검사한다.

## 2. 단계별로 어떻게 하는가

### 2-1. 입력을 좌표로 (`kakao-local.client.ts` geocode)

"성수동", "홍대입구역" 같은 자유 입력을 카카오 키워드 검색 첫 결과의 좌표로 바꾼다. 이후 모든 검색은 이 좌표 + 반경(차 없음 3km, 차 있음 5km)으로 한다. 지역명 문자열이 아니라 좌표를 기준점으로 잡아야 "성수동"과 "성수역"이 같은 캐시를 탄다.

### 2-2. 두 갈래 동시 수집 (`area-cache.service.ts`)

```ts
const [kakaoPlaces, extracted] = await Promise.all([
  this.kakao.collectAround(anchor, radiusM),   // 지도: 카페·음식점·문화시설·명소 각 최대 45건
  this.hints.collect(locationQuery, anchor),   // 웹: 블로그·인스타·일반 글에서 장소 언급
]);
```

- **지도 검색**은 "이 반경 안에 실제로 뭐가 있나"를 준다. 주차·가격·분위기는 없다.
- **웹 조사**는 "사람들이 뭘 추천하나, 분위기·가격·주차는 어떤가"를 준다. 좌표는 없다.
- 둘을 **이름으로 맞춘다**(2-4). 서로 없는 정보를 채워준다.

### 2-3. 웹 조사: 검색과 추출을 분리 (`llm/web-hints.ts`)

AI에게 "성수동 데이트 코스 찾아줘"라고 하면 검색+읽기+정리를 한 번에 하느라 느리고 출처가 불분명하다. 그래서 둘로 쪼갠다.

1. **검색은 검색 API(Tavily)** 가 한다. 출처 종류별로 도메인을 제한해 따로 검색한다.
   - 블로그: `blog.naver.com, tistory.com, brunch.co.kr`
   - 인스타그램: `instagram.com` (해시태그 모음 페이지 `/popular/` 는 버리고 게시글만)
   - 웹: 제한 없음
2. **추출은 AI**가 한다. 검색 본문에 `[1] (블로그) 제목…` 번호를 붙여 넣고, JSON 스키마를 강제해 뽑는다.

```ts
{ placeName, hint, priceHintKrw, parking: "yes"|"no"|"unknown", sourceIndexes: [1, 3] }
```

배운 점:
- **출처 번호를 본문에 박고 AI가 번호를 돌려주게** 하면 "이 힌트가 어느 글에서 왔는지"가 남는다. AI가 URL을 지어내는 문제가 사라진다.
- 추출 호출을 출처별 3개로 **나눠서 동시에** 보내면 프롬프트가 작아져 무료 등급 모델도 3~5초에 끝난다. 한 번에 넣으면 20초 넘게 걸렸다.
- 인스타그램은 직접 긁지 않는다. 검색엔진에 색인된 공개 게시글 캡션만 쓴다. 약관 문제가 없다.

### 2-4. 이름 매칭 (`places/mention-match.ts`, `common/text.ts`)

블로그의 "블루보틀"과 지도의 "블루보틀 성수점"을 같은 곳으로 봐야 한다.

- 지점명 제거(`stripBranch`: 끝의 "○○점"), NFKC 정규화, 공백·구두점 제거
- 3자 이상이고 한쪽이 다른 쪽의 접두어면 같은 곳
- 후보가 여럿이면 더 긴(구체적인) 이름을 고른다
- 지도에 없는 상호는 카카오에서 **추가로 찾는다**(상한 20). 블로그에만 나오는 숨은 가게가 이렇게 후보에 들어온다.

같은 장소에 언급이 여럿이면: 주차는 하나라도 "가능"이면 가능, 가격은 중앙값.

### 2-5. 코드 필터 (`recommend/filters.ts`, `schedule.ts`)

AI에 넘기기 전에 규칙으로 걸러낸다.

- 차 있음 → 주차 "불가"만 제외. "정보 없음"은 통과시키고 화면에 그대로 표시한다. (정보 없는 걸 빼면 후보가 안 남는다)
- 약속 시각부터 6시간 안에 열리지 않는 곳 제외. 영업시간 데이터가 없어서 **카테고리 규칙**으로 대신한다 (술집 17~02시, 브런치 9~15시, 미술관 10~18시 월휴무…).
- "다른 코스 더 보기"면 이미 본 장소 제외. 단 남는 후보가 15개 밑이면 빼지 않는다.

### 2-6. 후보 줄이기 (`recommend/select-candidates.ts`)

후보가 190개면 다 넘기지 않는다. 60개로 줄이되 **언급 많은 순 70% + 무작위 30%**. 무작위가 섞여야 같은 입력에 매번 다른 코스가 나온다. 무작위 함수는 밖에서 주입해 테스트에서 고정한다.

### 2-7. AI 조합 (`llm/compose-courses.ts`)

프롬프트에 넣는 것:
- 조건(성향·예산·차·시각·요일)
- 후보 60줄: `id | 이름 | 카테고리 | 가능 시간대 · 머무는 시간 | 언급 [블로그/인스타/웹] | 가격 | 주차 | 힌트`
- 규칙: 후보 id만 쓴다, 2~4곳, 언급 있는 곳 우선, 시간표 지킨다, 코스끼리 다르게

출력은 JSON 스키마로 강제한다: `{ courses: [{ title, reason, stopPlaceIds }] }`. 자유 문장으로 받으면 파싱이 깨진다.

`thinkingLevel: MINIMAL`로 둔다. 후보 60개 조합은 깊은 추론이 필요 없고, 기본값은 16초, 최소는 4초였다.

### 2-8. 검증 (`recommend.service.ts` materialize, applySchedule)

AI가 낸 것을 코드가 다시 본다.

- 후보에 없는 id 제거, 코스 안 중복 id 제거
- 알려진 가격 합 × 2 > 예산이면 코스 탈락. 가격 모르는 장소는 합에서 빼고 "+α" 표시
- 만나는 시각부터 머무는 시간 + 이동 시간을 누적해 도착 시각 계산, 가능 시간대 밖이면 탈락
- 시간표 검사는 **두 번**: 경로 API를 부르기 전 어림값(15분)으로 한 번(쿼터 절약), 실제 경로로 한 번 더

### 2-9. 경로·주차 (`recommend/routes.service.ts`, `collectors/kakao-routing.client.ts`)

장소 사이 구간마다 카카오 대중교통/도보/자동차 경로를 묻는다. 버스 번호, 정거장, 환승, 요금이 온다. 차 있으면 장소마다 300m 안 가장 가까운 주차장(카테고리 PK6).

- 같은 구간을 두 코스가 쓰면 한 번만 묻는다 (Promise 캐시 = 단일 비행)
- 실패하면 직선거리 × 1.3으로 어림하고 `estimated: true`로 표시한다. 조용히 지어내지 않는다.

## 3. 캐시와 비용

| 자원 | 무료 한도 | 한 번 추천에 | 대책 |
| --- | --- | --- | --- |
| 카카오 로컬 검색 | 10만/일 | ~13 (카테고리 12 + 지오코딩 1) | 지역별 일주일 DB 캐시 |
| 카카오 대중교통·도보 경로 | 각 1천/일 | 5~15 | 구간 Promise 캐시(프로세스) |
| 카카오 자동차 경로 | 1만/일 | 5~15 | 같음 |
| Tavily 검색 | 1천/월 | 5 | 지역 캐시로 첫 조사에만 |
| Gemini | 무료 등급 | 4 호출 | 모델 분리(추출 3.5-flash, 조합 3.5-flash) + 실패 시 대체 모델 |

**지역 캐시**(`AreaFetch`)가 핵심이다. 같은 좌표 110m 격자 + 반경이 일주일 안이면 지도·웹 조사를 건너뛴다. 첫 조사 13~20초, 캐시 적중 4~5초.

**실패한 조사는 캐시하지 않는다.** 웹 힌트 수집이 실패했을 때 지도 장소만으로 결과를 내지만, 그 반쪽 결과를 일주일 캐시로 굳히면 안 된다. 다음 요청이 다시 조사한다.

## 4. 이 프로젝트에서 배운 것 (다른 데도 쓸 수 있는 것)

1. **AI는 "구조화"와 "취향 판단"에만.** 사실(좌표·경로·시간)은 API, 규칙(예산·주차·시간)은 코드. AI가 한 판단은 코드가 다시 검증.
2. **출력은 항상 JSON 스키마.** zod로 스키마를 만들고 제공자(OpenAI/Gemini) 모두 같은 스키마를 강제한다. `llm/llm-client.ts`가 제공자를 추상화해서 키만 바꾸면 갈아탄다.
3. **검색과 읽기를 분리.** 검색 API가 찾고, AI가 읽는다. 출처 번호를 본문에 박아 AI가 번호로 답하게 하면 환각 URL이 없다.
4. **긴 호출은 쪼개서 병렬.** 프롬프트 크기가 속도를 결정한다. 3개로 나누면 3배 빠르고 하나가 실패해도 나머지는 산다.
5. **모르는 값은 "모름"으로 표시.** 가격 없으면 "+α", 주차 정보 없으면 "정보 없음", 경로 실패면 "어림". 0이나 빈 값으로 두면 필터가 거짓 통과한다.
6. **캐시 단위를 사용자 입력이 아니라 정규화된 키로.** 좌표 격자 + 반경. "성수동"과 "성수역"이 같은 캐시를 탄다.
7. **무료 등급 모델은 느리고 자주 죽는다.** 재시도 + 대체 모델 + 실패해도 결과가 나오는 설계(힌트 없으면 지도만으로).
8. **속도 튜닝은 로그부터.** `GeminiClient`가 호출마다 모델·시간·토큰을 찍는다. 3.6-flash 32초 vs 3.5-flash 3초는 로그를 보고 나서야 알았다.
9. **약관을 먼저 본다.** 네이버 검색 API는 결과의 AI 입력·저장을 금지해서 뺐고, 인스타그램은 색인된 공개 글만 쓴다. 이력서에 올릴 프로젝트면 더 그렇다.
10. **테스트는 판정 로직에.** 예산 계산, 주차 필터, 이름 매칭, 시간표, 후보 선별은 전부 순수 함수라 54개 테스트가 API 없이 돈다. AI 호출은 테스트하지 않는다.

## 5. 아직 못 한 것

- 실제 영업시간 (구글 플레이스는 카드 등록 필요). 지금은 카테고리 규칙이라 개별 가게 휴무는 못 잡는다.
- 경로 캐시를 DB에 (지금은 프로세스 메모리라 재시작하면 사라짐). 대중교통 경로 하루 1천 건이 첫 병목.
- 가격 힌트가 드물다. 블로그 요약문에 가격이 잘 안 나온다. 본문 전체를 가져오면(Tavily `include_raw_content`) 나아질 수 있으나 토큰이 늘어난다.
